# HuduFreight truthfulness and UX audit — 2026-10-20

## Scope and evidence limits

Source audit of the 15 requested routes, their backend registrations, queried tables, action handlers, integration code and styles. The browser reached sign-in; the user explicitly chose to continue with source audit. No authenticated live-page visual inspection, provider-health check, database-content provenance check, CRUD execution or fleet regression tests were performed in this audit. “Database-backed” below means an implemented, registered persistence path, not proof that a displayed record represents a real-world event. No application code was changed.

Current working-tree files were inspected, including uncommitted freight changes. Earlier UI checks or statements about working integrations do not establish the truth of this newer code.

## Classification

- **Implemented:** UI calls a registered endpoint that reads/writes tenant data.
- **Derived:** a calculation or heuristic over stored inputs; distinguish it from direct telemetry.
- **Synthetic:** hardcoded business facts, simulated success or fabricated fallback records.
- **Incomplete integration:** both domains may exist, but the expected link is absent or only partially exposed.

## Highest-priority evidence

1. **Synthetic fleet data and apparent verification:** `apps/web/src/lib/freightFleetData.ts:85` defines a Volvo, invented operational figures, driver, documents and alerts. `getFleetVehicleById` at line 512 returns the first fixture even for an unknown ID. `TrackingVehicleDetail.tsx:100` starts a full fallback; line 185 substitutes it after API failures. Several sections use `canonicalFleetVehicle` even after successful API loads: driver/phone near line 568, document cards near line 638 and 3D/payload near line 695. Its document modal at line 1073 displays “Verified Regulatory Compliance Document” / “Valid & Active” without opening actual file bytes or verifying an issuer. This is a critical trust defect.
2. **Cargo can appear successful after failure:** `TrackingCargoLoading.tsx:309` creates synthetic approved manifests, line 395 substitutes fixture cargo, and line 478 simulates packing after an API failure. `cargoLoading.routes.ts:229` persists the 2,000 kg placeholder weight. A database write can therefore contain synthetic assumptions too.
3. **Route-planner decorative controls:** `TrackingRoutePlanner.tsx:96` always uses the same OSRM driving request. Destination input and priority selector near lines 248–270 do not affect that request. The top-right widget around line 200 hardcodes 6,000 kg.
4. **Data provenance:** migration `062_seed_detailed_vehicles.sql:13` explicitly seeds sample vendors, drivers, vehicles, GPS positions, trips and reminders into the first tenant. Migration 065 adds sample truck records/images. Database-backed rows can therefore still be demonstration data; this audit did not query the user's live rows to identify which seeds remain.
5. **Missing or partial domain links:** `warehouse.routes.ts:28` states that occupancy is based on parts stock; `seal-equipment.routes.ts:43` explicitly distinguishes SEAL from Tracking's locations/parts. `DepotPage.tsx:116` only selects depot/ad-hoc subjects, while `depot.routes.ts:176` contains the conditional SEAL mirror. Fleet document/reminder references occur in Tracking routes and aggregates, with no direct ComplyOS/Tasks bridge found.

## Cross-cutting UX and engineering priorities

### P0 — stop misleading operational decisions

- Remove hardcoded fleet/driver/compliance facts from production paths. A fixture must be a clearly labelled, isolated demo mode.
- Never turn a failed API request into approved, dispatched, saved or fully packed state. Keep the user's inputs and show a retryable error.
- Remove unsupported compliance-verification claims and invented contact details. Unknown IDs must show not found.
- Distinguish unknown telemetry from zero, stale observations from live events, estimates from actual progress, and no evidence from perfect performance.

### P1 — make the advertised workflows complete

- Share or explicitly bridge SEAL locations/inventory and depot subjects; link ComplyOS documents and Tasks reminders with real IDs, tenant validation and synchronization behavior.
- Make dispatch create/associate an actual trip if that is the promised workflow.
- Remove or implement planner text search, routing preferences and alternative route tabs. OSRM driving estimates are not truck-clearance/hazardous-cargo/live-traffic optimization.
- Add auditable part movements and location assignment; file-backed fleet documents; actual reminder delivery and task ownership.

### P1 — consistent error, responsive and accessible UX

- Use shared DataTable, SearchToolbar, Button, Badge, QueryState and loading components consistently. Several maintenance/compliance registers still use raw tables and hand-styled tiny action buttons.
- Separate empty, offline, forbidden, entitlement and server-error states. Current `.catch(() => [])` patterns frequently make an outage look like an empty business.
- Replace fixed multi-column forms and overlapping map widgets with narrow-width layouts, drawers or dedicated pages. Drivers/vehicles have useful breakpoints, but that does not establish that every panel/table works on mobile.
- Add accessible names and keyboard activation for clickable cards/icon controls. Do not rely only on color for severity, low stock or status.
- Standardize fleet-status taxonomy across directory, details, live map and cargo views. Current pages can tell conflicting stories about the same vehicle.

### Further backend validation required

Registered APIs and explicit tenant filters are positive, but they are not a production security certification. Some create handlers accept foreign IDs without an explicit same-tenant lookup (for example fleet documents, dock appointments and cargo-item/dispatch links); several payloads are TypeScript casts rather than runtime schemas. Cargo packing/status mutations do not consistently enforce an approved-plan state machine. These are source-review concerns; no cross-tenant exploit or mutation was attempted.

## Recommended sequence

1. Isolate/remove synthetic production fallbacks and fake verification messages.
2. Establish one source of truth and status taxonomy for vehicles, drivers, trips and cargo.
3. Complete the four requested domain bridges: Warehouse→SEAL, Depot→SEAL, Documents→ComplyOS, Reminders→Tasks.
4. Fix planner controls and evidence labels; expose real errors and provenance.
5. Run authenticated desktop/mobile checks and disposable-tenant integration tests for persistence, permissions and cross-tenant foreign IDs.
