## Reproduced release blockers

### P1 — Voided credits still reduce outstanding balances

`apps/api/src/routes/invoices.routes.ts:286`, `617`, `1297`, `1712` compare credit-note status against `'Void'`; the actual credit-note states are `'POSTED'` and `'VOID'` (`credit-notes.routes.ts:268`, `321`). A voided credit therefore remains in the credit sum.

Fresh reproduction: issue a TZS 100 invoice, issue a linked TZS 100 credit, then void that credit. All writes succeed. Invoice statistics show outstanding **0**, although it was **100** before the credit and should return to 100 after voiding. The same predicate is used by the receivables and payment paths, so the bug can also route a valid receipt into overpayment credit instead of clearing AR.

Required: consistently sum eligible POSTED credits, use tenant-scoped predicates, and add issue/void/payment lifecycle assertions across stats, lists, statements, aging and GL. Credit issue/void must also recompute the source invoice's settlement status; creation currently only appends activity.

### P1 — Aged receivables still ignores credits

`apps/api/src/services/gl.service.ts:825` computes unpaid as invoice total minus receipts, without linked credits. The finance aged-receivables route calls this service (`routes/gl.routes.ts:536`); the UI uses that endpoint.

Fresh reproduction: issue TZS 100, then fully credit it. Aging total remains unchanged instead of falling by 100. In the probe's cumulative disposable dataset the expected total was 200; actual total was 300. This proves the readiness report's claim that allocation is fixed across aging is inaccurate.

Required: a shared balance calculation and source-to-GL reconciliation tests, including partial/full credit, payment before/after credit, void and refund behavior. Do not fix only the dashboard aggregate.

### P1 — Bank matching accepts an opposite-direction transaction

`apps/api/src/routes/bank-reconciliation.routes.ts:173` accepts either `statement − ledger` or `statement + ledger` within tolerance. The CSV importer already normalizes credits/deposits as positive and debits/withdrawals as negative, so ignoring sign is not a harmless bank-format accommodation.

Fresh reproduction: a **+100 deposit** statement line successfully matches a **−100 bank withdrawal** journal line, HTTP **200**. Correct behavior is rejection. Unequal-amount rejection is fixed, but reconciliation still cannot be trusted.

Required: compare signed normalized amounts. Explicitly establish statement/account currency and date policy, and cover opposite signs, withdrawals, deposits, duplicates and concurrent matching. Currency is currently selected but not checked; the match endpoint only rejects VOIDED journals rather than requiring a defined eligible state.

### P1 — FX conversion still skips rates below one

Invoice issuance (`invoices.routes.ts:971`), draft issuance (`1116`), receipts (`1322`), credits (`credit-notes.routes.ts:280`) and bill payment use a `rate > 1` conversion guard. Currency difference, not rate magnitude, determines whether conversion is needed.

Fresh reproduction: issue foreign-currency 100 at rate **0.5**. Expected reporting-currency AR is **50**; actual AR is **100**. A deliberately synthetic positive rate exercises a valid conversion branch; this is not a market-rate assumption. The successful USD/TZS rate-2650 receipt probe does not establish general multi-currency readiness.

Required: validate finite positive rates, convert consistently for all supported currencies/rates and keep rounding balanced across net/tax/total. Add sub-unit, same-currency and foreign-currency settlement/credit/reversal coverage.

## Still needs engineering work

- Credit-note statistics still sum unlike currencies in `credit-notes.routes.ts:140`, and `CreditNotes.tsx:349` still displays the legacy total rather than `creditedByCurrency`.
- `FinOpsShell.tsx` still eagerly imports finance page modules; no route-level lazy split was found. Legacy/unbounded report, expense, journal and export paths need bounded server-side reads and measured acceptance.
- `FinanceCashFlow.tsx:19–21` still converts local-midnight month boundaries to UTC ISO dates, shifting dates backward in Africa/Dar_es_Salaam. Backend finance-date unit tests do not validate this frontend function.
- POS retry-posting (`pos.routes.ts:509`) still reads its snapshot/existing journal and posts in separate transactions without an atomic claim. A concurrent retry test and protection remain necessary.
- VAT close (`vat-periods.routes.ts:223–255`) still has no requirement for a current independently approved tax preparation. The reviewer workflow exists but is not an enforced close gate.
- Comprehensive role/permission, employee-claim scope and desktop/mobile/error/retry acceptance remain open. This review did not run a new exhaustive browser matrix.
