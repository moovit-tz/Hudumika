## P1 — Simultaneous POS accounting retries create duplicate journals — FIXED

Endpoint: POST /v1/finance/pos/sales/:id/retry-posting (pos.routes.ts:510 onward).

**Root cause:** The route used three separate transactions: (1) read the sale and check for an existing journal, (2) post the journal via GLService.post, (3) update the sale status. Two concurrent callers both observed no journal in step (1), both posted in step (2), but only one succeeded in step (3). The extra journal duplicated cash/revenue posting.

**Fix:** Consolidated into a single atomic `withTenant` block with `FOR UPDATE` on the sale row. `postSaleJournal` now accepts an optional `Transaction<Database>` parameter, forwarded to `GLService.post`, so the journal is created inside the same transaction that holds the lock. The winner posts the journal and marks the sale COMPLETED; any concurrent caller serializes behind the `FOR UPDATE` lock, sees the sale is no longer `POSTING_FAILED`, and returns 409. An existing-journal check inside the lock provides idempotency.

**Verified:** P1 #10 permanent regression tests — seed a `POSTING_FAILED` sale with a shift and CASH payment, then fire 3 concurrent retry-posting requests via `Promise.all`. Exactly 1 succeeds (200), 2 are serialized out (409). A follow-up query confirms exactly 1 POSTED journal entry for the sale.
