# FinOps sixth follow-up review — 22 October 2026

## Decision

Not ready for unrestricted production approval. Previous focused credit/FX/commit fixes now have broader permanent coverage, but new journal pagination introduces a confirmed runtime failure. The readiness report's statement that engineering hardening is complete is unsupported by current behavior.

## Confirmed regression — P1 journal register fails

GET /v1/finance/journal-entries?page=1&page_size=10 returns HTTP 500, even in a disposable tenant with no journal rows.

Error: column "journal_entries.id" must appear in the GROUP BY clause or be used in an aggregate function.

At apps/api/src/routes/gl.routes.ts:338, the count query adds count(*) to a builder that already selects ordinary journal columns. Kysely select() is additive; it does not replace the selection. Use clearSelect() before counting, or a separate filtered count query. Keep stable page ordering, verify filters/counts across multiple pages and add permanent HTTP register coverage. This review did not fix application code.

## Other remaining findings

- VAT close now requires an approved preparation to exist, but does not compare its source_hash with the current taxPreparationContext hash. An older approval still satisfies the query after source changes. Review approval itself checks freshness, but the consuming close action must do so too, within an appropriate transaction/locking policy. This is a code finding; no new VAT filing/close mutation probe was run.
- POS retry-posting still reads its sale/existing journal snapshot and posts in separate transactions, with no atomic claim in the inspected route. The existing duplicate lookup does not establish concurrent retry protection. No new POS concurrency reproduction was attempted. Do not mark this complete without a permanent concurrent acceptance test and a proven invariant.
- Credit total display now converts currency buckets using the shared useCurrency helper. This improves on adding unlike units, but is a display-rate conversion, not reconciliation to historical posting rates. Live/fallback-rate labeling and accounting acceptance still require verification.
