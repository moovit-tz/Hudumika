# POS audit — 24 October 2026

**Verdict: no production green light.** The tested build has reproducible checkout, inventory, refund and cash-accounting defects. This is a local working-tree audit, with concurrent development occurring in the same checkout, not a certification of a deployed release or every possible scenario.

## Reproduced release blockers

| Priority | Defect and evidence | Required correction |
| --- | --- | --- |
| P1 | **Default browser checkout is rejected.** `FinancePos.tsx` sends `notes: saleNotes.trim() || null`; `checkoutSchema` allows an optional string but not null. The exact browser payload returns HTTP 400. | Align the request/validation contract for empty notes and cover a real UI checkout with a disposable tenant. |
| P1 | **Tracked inventory can be bypassed.** A tracked chocolate product sold successfully for quantity 1,000 without a location, despite only a small quantity being stocked. The stock movement block only runs if `inventory_location_id` is provided. | Require a valid pickable location and linked inventory item for tracked goods, honor stock policy, and fail closed. Explicitly define untracked products/services. |
| P1 | **Currency can be relabeled without conversion.** A TZS 100 service plus 18 tax was accepted as USD 118 by changing only request currency. | Validate all product/price/tender currencies on the server. Apply a defined FX policy or reject mismatches; group drawer/report balances by currency. |
| P1 | **Checkout retry duplicates the sale.** Two identical POSTs carrying the same `idempotency-key` returned distinct sale IDs. | Add tenant-scoped persisted idempotency, payload hashing and concurrent replay handling; preserve the key in the UI until a definitive outcome. Test timeout-after-commit and concurrent duplicate requests. |
| P1 | **Stock refund fails in the deployed local schema.** Normal restocking returns HTTP 400 with `inventory_movements_movement_type_check` because `return` is rejected. Migration 123's movement enum omits `return`, while the service uses it. | Add an additive migration, verify deployed schema and exercise issue/return/COGS reversal end to end. Do not edit the applied migration. |
| P1 | **Refund is not atomic.** With stock return forced to fail, the source GL entry was already voided while the sale remained completed. This also occurs through the real constraint failure above. | Lock the sale and perform GL reversal, inventory return, refund status and durable event scheduling in one transaction. Ensure retry/concurrency cannot duplicate a refund or strand a reversal. |
| P1 | **Held carts cannot be saved.** A normal POST `/holds` returns HTTP 400/Postgres 22P02. An array is passed directly into a JSONB field; the driver encodes it incompatibly. | Use the existing JSON serialization pattern and test save/list/restore plus concurrent claim and foreign reference rejection. The test stops at failed creation, so successful restore is not claimed. |
| P1 | **Drawer cash omits failed-posting sales.** After receiving 118 cash and returning POSTING_FAILED, expected drawer cash changed by zero. Both bootstrap and close calculations filter only COMPLETED sales. | Separate payment/stock completion from accounting delivery status; include actual cash receipts pending GL posting and model cash refunds in the drawer that pays them. |
| P2 | **Tender rounding is inconsistent.** Tenders 59.005 and 58.995 produce stored payment amounts totaling 118.01 while `amount_paid` is 118.00. | Reject unsupported precision or normalize once in minor units before calculating paid/change and posting. Cover zero-, two- and three-decimal currencies under an explicit supported-currency policy. |

Source locations are in `apps/api/src/routes/pos.routes.ts`: checkout schema near line 29; held-cart insert near 330; checkout totals near 448; optional stock movement near 469; separate GL posting near 487; refund reversal before stock/status near 562. Related UI request is in `apps/web/src/pages/FinancePos.tsx`, function `checkout`.

## What passed

- Authentication required; a valid JUNIOR operations user denied access; SALES user denied manager refunds, posting retry and another user's cash movements.
- Foreign product, customer and inventory-location IDs rejected; other tenants cannot retrieve sale details/history or manipulate the owner's shift.
- Capability-disabled workspace retains GET access and rejects checkout mutations.
- A register is required; concurrent register opening gives one 201 and one 409; closed registers reject checkout and new cash movements.
- Server prices override an injected client price. Tax/discount and mixed cash/card change calculate correctly for ordinary two-decimal inputs; resulting journal balances.
- Short tender, noncash overpayment, excessive discounts, zero quantity and oversized pagination rejected. Rejected checkout leaves sale count unchanged.
- Duplicate-line insufficient-stock rollback preserves the pre-request stock level. Competing last-stock sales produce one successful sale and one rejection; stock never goes negative in that test.
- Service-only refund succeeds once, rejects a repeat and disappears from completed-sale reporting. This does **not** establish stock-refund safety.
- Failed GL posting returns 202; concurrent manager retries give one success and one conflict. The existing regression suite separately verifies exactly one posted journal.
- Literal search metacharacters and exact receipt/status filtering behave correctly.
- Receipt profile persistence, tenant isolation, settings role restrictions, malformed profile rejection, escaping, template variants, device preferences, fresh saved-profile loading and fetch-failure handling pass their targeted tests.

- Increasing quantity recalculates the displayed subtotal/tax/total. Split adds a separate card tender row. Submit remains disabled with insufficient tender and with an empty cart.
- Catalogue next-page changes the displayed product range from 1–12 to 13–24 of 112.
- History opens an existing receipt with the saved retail template, business logo/contact/tax identity, receipt identifier, actual lines, tax and total.
- At 390px the receipt dialog spans x=16–374; document width remains 390px. At 1440px document width remains 1440px. This establishes these observed widths, not every viewport, zoom or assistive technology.
- **Additional currency display defect:** the existing USD 77.88 receipt is correct in history/receipt, but the empty-cart desktop shift header labels the shift's 77.88 sales as TZS. The route aggregates currencies without grouping, and the UI uses the cart currency (default TZS) for summaries. This needs a currency-aware register and reporting design.
- An initial blank page logged `useAuth must be used within an AuthProvider` from AutoSEO. Reload recovered to the normal lock screen; unlocking restored the POS. This is an observed development/runtime incident, not yet an isolated persistent production defect. Concurrent edits/HMR occurred during this audit.

## Further source-review risks and unverified capabilities

These are not represented as passed tests:

- Checkout commits stock/sale before sales GL and event emission. An event failure is caught as a posting failure even after the journal succeeds. Use an atomic source transaction plus the existing appropriate durable delivery mechanism; preserve recovery semantics.
- Shift close and cash movements do not lock the same shift row as checkout. Test deterministic close-versus-sale and close-versus-cash-movement races before release.
- Inventory service requires a batch for batch-tracked goods, but POS checkout accepts/passes no batch. FEFO, expiry, recall blocking, serials, scales and unit conversion need explicit POS capabilities and tests. Chocolate/food batch traceability is not certified here.
- Return costing reads current average cost, while sale lines store their original cost. Test a receipt/cost change between sale and return and define how the original COGS is reversed.
- CARD, MOBILE_MONEY and BANK are recorded tender types in this route. No authorization, capture, webhook settlement or provider refund is invoked here. Do not describe a locally recorded refund as evidence that money was refunded by a processor.
- The Bill control displays guidance about generating a linked invoice, while the backend explicitly keeps POS receipts out of `sales_invoices`; verify or correct that user promise. Partial/item-level refunds are absent from this refund schema.
- Quota checks read usage before checkout and count after response. Concurrent quota enforcement, exhausted plans, suspended tenants, API-key scopes, CSRF/cookie flows and the complete role matrix need dedicated verification beyond the selected checks.
- Browser network-loss recovery, lost checkout responses, concurrent held-cart restoration, terminal reload recovery, offline policy, long-running shifts and timezone day boundaries remain to be tested.
- No physical 58/80mm/A4 printer, OS driver, cutter, cash drawer, scanner hardware, print cancellation, paper exhaustion, copy output or PDF paper fit was tested. Screenshot/HTML tests do not prove hardware output.
- No sustained load/soak test, independent penetration test, staging processor acceptance, restore/failover exercise or monitoring/alert drill was run. This is not a full platform security review.

## Way forward

1. Fix the reproduced checkout/hold contract failures and schema mismatch. Add migration verification to release gates.
2. Make checkout idempotent, enforce currency and tracked-stock rules server-side, and make refunds atomic with original-cost handling.
3. Separate operational payment/stock state from posting delivery state; reconcile drawers by currency and drawer ownership, including failed posting and later refunds.
4. Keep these regression assertions; obtain a clean run, then add deterministic race, outage/retry and batch/expiry tests.
5. Run cashier/manager journeys in a disposable browser workspace and staging payment/printing hardware acceptance. Complete load, security and recovery gates against a pinned release before a production decision.
