01 · The promise

One platform. Specialist products. Shared trust.

Hudumika helps organizations coordinate work, money, people, records and services. A user should understand what is happening, what it means and what they can safely do next—on a phone in the field or at a desk reviewing an organization-wide report.

Make the next action clear

Put the user’s task and its current state before internal terminology or promotion.

Make important facts dependable

Use real system state. Label estimates, stale data, missing integrations and unavailable services.

Preserve context

Identity, tenant, people, contacts, notifications, audit history and finance should connect consistently.

Respect consequences

Financial, legal, safety, HR, customs and customer actions need validation, permissions and recovery.

02 · Decision principles

How we choose what to build

Use these principles when scope, speed, consistency and local needs compete. Record significant exceptions and their owner.

1People before internal structure

Design around real users, roles, goals and working conditions—not the org chart or database schema.

2Clear before clever

Use familiar words, visible labels and explicit states. Progressive disclosure can hide complexity, not essential meaning.

3Trust through truth

Never simulate a successful send, payment, sync, approval or delivery. Show queued, processing, complete, rejected or unknown accurately.

4One system, useful variation

Share controls and behavior. Allow product-specific patterns only for validated domain needs, expressed as reusable and reviewed extensions.

5Choice with guardrails

Explain material effects before spending money, exposing data, contacting customers, changing access or submitting to a regulator.

6Reliability is part of the interface

Design loading, empty, partial, offline, denied, stale, conflict and failure states. Keep user work recoverable.

7Privacy and least access

Show only what a person needs for their role. Enforce permissions server-side across search, exports, notifications and AI context.

8Accessibility is baseline quality

Support keyboard, screen readers, contrast, focus, reduced motion, touch, zoom, localization and low-connectivity conditions.

03 · Shared visual language

Use the system; don’t freeze it in a page

The runtime design system owns exact values and component behavior. Read docs/DESIGN_SYSTEM.md before adding UI.

  • Brand: Keep Hudumika’s platform identity and configured app accents. Do not copy another company’s visual identity or proprietary assets.
  • Color: Use semantic tokens for meaning and app accents for identity. Never make color the only status signal. Use contrast-safe tokens for filled actions.
  • Shape and density: Use global radii, spacing and control-height tokens. Compact layouts must remain readable and usable.
  • Typography: Use the configured type scale. Keep titles, section headings, labels, body text and metadata distinct.
  • Icons: Use the shared library. Pair icons with labels for unfamiliar or high-impact actions; icon-only actions need accessible names and hints.
  • Surfaces: Cards group related information and work. Avoid decorative card sprawl and keep critical actions visible without page-wide horizontal scrolling.
  • Motion: Explain changes and preserve orientation. Respect reduced motion; never imply completion before confirmation.

Responsive rule: Design narrow-first. Preserve task order, labels, values and primary actions; reflow grids and detail panels; use intentional table behavior. Check 320px, 375px, tablet, desktop and 200% zoom.

04 · Voice & content

Clear, capable, considerate and candid

Hudumika’s voice stays consistent. Tone changes with the user’s moment.

MomentUse this toneMake sure the user knows
Routine workBrief and neutralThe task or result, without filler
SuccessCalm and specificWhat completed and what happens next
ValidationHelpful and localWhat this field needs and how to correct it
Technical issueSteady and candidWhat was affected, whether data was saved, and a recovery step
Risk or complianceSerious and preciseFacts versus signals, evidence and review path
Money or irreversible actionExplicit and completeAmount, currency, recipient, timing and consequence
  • Put the key fact first. Use one action per button: Save changes, Review invoice.
  • Never blame the user or use vague “Something went wrong” when the cause is known.
  • Use consistent names. Define specialist terms for users who may not know them.
  • Format dates, time zones, currencies, units and large figures for locale and context.
  • Disclose estimates, AI assistance and uncertain matches. Let users verify consequential output.

Blocking-message pattern: Say what happened. Explain whether the action or data was saved, sent or charged. Give a safe next step.

06 · Product architecture

Shared services, clear boundaries

  • Hudumika core: identity, tenancy, entitlements, design language, APIs, audit events and accessibility behavior.
  • Products: own specialist workflows and data semantics; use documented Ondi identity and authorized APIs for shared services.
  • Shared services: contacts, email, SMS, tasks, finance, HR, documents and compliance expose stable permission-aware APIs. No cross-product table shortcuts.
  • Events: define ownership, version, tenant scope, idempotency, retries and audit requirements; distinguish queued, accepted and confirmed outcomes.
  • Entitlements: backend checks enforce access. A locked feature explains its value without pretending it is active.

Definition of ready

Identify users and roles, job, success measure, mobile/low-connectivity conditions, data sensitivity, failure states, source of truth, integrations and localization needs.

Definition of done

  • Shared components and tokens used; exceptions are reviewed.
  • Relevant loading, empty, partial, success, denied, stale/offline and failure states work.
  • Keyboard, screen reader, focus, contrast, motion, touch, zoom and small-screen behavior checked.
  • Server-side tenant access tested, including a cross-tenant denial case.
  • High-impact actions have confirmation, idempotency, audit trail and recovery.
  • Copy, dates, time zones, currency, precision and provenance verified.
08 · Extend & measure

Improve the system with evidence

  1. Search the catalog and existing code.
  2. State the user need and why existing components cannot solve it.
  3. Design reusable behavior, including errors and recovery.
  4. Check accessibility, responsiveness, localization, tenant theme, density and dark mode.
  5. Put cross-product patterns in the shared system; keep one-product workflows composed from shared primitives.
  6. Document the rule, owner and review date; migrate old patterns in safe increments.

Measure task completion and time, errors and retries, abandonment, support contacts, accessibility defects, mobile overflow, stale/conflicting data, privacy incidents, shared-component adoption and user confidence. Do not improve speed by shifting risk or hidden work to another team.
