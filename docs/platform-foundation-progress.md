## Phase 3 — Scoped Parties API for independent apps (done, live-verified)

- New route file `apps/api/src/routes/platform-parties.routes.ts`, registered at `/v1/platform/parties` in `index.ts`.
  - `GET /search`, `GET /by-external-ref/:source/:ref`, `POST /` (search-or-create, idempotent via `party_external_refs`).
  - Gated by the existing `x-api-key` mechanism + a new `platform.parties` scope value (checked ad hoc in-route, same pattern as `finance-documents.routes.ts`'s `apiKeyScopes` check) — no new auth code path.
  - Write access further limited by the key's existing `read_only` flag (generic, enforced in `middleware/auth.ts`).
- Provisioning a key for a tenant: issue via the existing `POST /v1/api-keys` with `scopes: ['platform.parties']` — requires the tenant to have `platform.parties` in its granted-features set first (e.g. via `tenant_settings['enabled-apps']: {'platform.parties': true}` override), since `api-keys.routes.ts` validates requested scopes against entitlement.
- **Found and fixed a real bug while building this**: `party.service.ts` and `party-visibility.ts` assumed every actor had a real `users.id` UUID. An API-key actor's `request.user.sub` is a synthetic `apikey:<id>` string, which would have made every ownership SQL comparison (`parties.owner_user_id = $1`) throw `invalid input syntax for type uuid`, and an INSERT with `created_by: 'apikey:...'` would have violated the FK. Fixed by making `PartyActor.id` (and the two SQL-builder helpers' `actor` param) `string | null`, with `null` meaning "no human actor" — resolves cleanly to SQL NULL / not-owned everywhere, confirmed via `canManage`'s own null-vs-null false-positive risk being guarded separately.
- **Live-verified** against the real dev DB + a running API server, with real provisioned tenants/keys (not mocked): invalid key → 401; valid key missing the `platform.parties` scope → 403; create → 201 with `created_by: null` (no crash); retried with the same `external_ref` → 200, same party id, no duplicate; search finds it; a `read_only` key's POST → 403; a second tenant's key searching for the first tenant's party → empty result (tenant isolation holds).
- Full-repo `npx tsc --noEmit` completed clean with respect to this work: the only 61 errors reported are pre-existing (invoices.routes.ts, settings.routes.ts, onsite-*.service.ts, carimages.service.ts, browser-audit tests missing DOM lib types) — none touch `vehicle_vendors`, `platform-parties.routes.ts`, `party.service.ts`, `party-visibility.ts`, or `client.ts`.

## Phase 3B — Ondi OAuth access to shared APIs (done, live-verified)

- The shared API now recognizes Ondi RS256 access tokens in `authenticate`, verifies issuer/client/user, checks the live consent and Redis revocation state, then applies the same tenant suspension, IP, maintenance, usage, entitlement, and route role gates as a Hudumika session.
- OAuth access is deny-by-default: only reviewed route prefixes map to resource scopes. Current mappings cover CRM, contacts, notes, email, SMS, invoices, compliance, employee records, shipments/orders, and document metadata. An unmapped API route returns 403 to OAuth access tokens. Employee, finance, and document scopes marked as requiring tenant approval remain blocked until that approval workflow is implemented.
- API operations require every registered scope for that resource/operation, so a contacts response cannot be accessed with only one of its basic/email/phone read scopes. Inactive scopes or scopes with unmet approval flags block the whole operation. Writes, deletes, and exports are distinct operations.
- Migration `741_standalone_app_api_scopes.sql` adds shared-service scopes for CRM, notes, email, SMS, compliance, finance, and basic HR. Finance and HR scopes are registered but explicitly unavailable until their required tenant-approval workflow exists. Existing high-risk payroll/identity/banking scopes remain similarly blocked.
- First-party apps now skip consent only for OIDC identity scopes. Requesting data scopes requires explicit user consent, and consent removal immediately invalidates API calls made with old tokens.
- Standalone apps must request the exact resource scopes they use and send the access token from their server-side backend. Do not put OAuth access/refresh tokens in browser storage. Tuma's current `OndiOidc` adapter still consumes only the ID token; a server-side shared-service adapter/token lifecycle is a separate Phase 4 change.
- Pure scope-routing tests and ESLint on the changed TypeScript files pass. Full-repo `npx tsc --noEmit` (run after Phase 3B's code was already in the tree) came back clean with respect to it — the only 61 errors are the same pre-existing ones noted under Phase 3 above.
- **Corrected a real mistake of my own**: I initially assumed (wrongly) that `contacts`/`invoices`/`orders`/`documents` had zero `oauth_resource_scopes` rows and added migration `742_standalone_app_api_scopes_gap.sql` to "fill the gap." All four resources already had rows from an earlier migration — `contacts` specifically with a deliberate three-way split (`contacts.basic.read`/`contacts.email.read`/`contacts.phone.read`) rather than one generic scope. Since `middleware/auth.ts`'s `ownsRequiredScope` check requires **every** registered row for a (resource, operation) pair at once, my inserted `contacts.read` silently added a fourth required scope on top of that design — stricter than intended, not a security hole, but wrong. Migration `743_remove_erroneous_oauth_scopes.sql` deletes the two rows 742 actually inserted (`contacts.read`, `documents.write`); the other six were no-ops against pre-existing rows via `ON CONFLICT DO NOTHING`. Net effect on the real schema: zero change, now confirmed correct.
- **Live-verified end-to-end**, with a real provisioned tenant/user/OAuth client/consent grant and a real signed RS256 access token (no mocks), against `/v1/contacts`: the correct granular read-scope set → 200 real response; a token claiming a scope its consent never granted → 401; a consented read-only token hitting a write route → 403 naming the missing resource/operation; a real, registered-but-unmapped route (`/v1/notifications`) → 403 "not enabled for Ondi app access"; deleting the consent immediately invalidates an otherwise-unexpired token → 401; setting the Redis revocation key for the token's `jti` → 401; a token whose `tenant_id` claim doesn't match where the consent was actually granted finds no grant and is rejected → 401 (no cross-tenant leak).
- **Unblocked local Redis for this verification, which also fixes the dev server generally**: `.env`'s `REDIS_URL` points at port 6380, but Docker Desktop's daemon wasn't running, so nothing was listening there — every Ondi OAuth request was failing closed with 503 ("revocation check unavailable"), and separately, `bootstrapJobs()`'s BullMQ queues were stuck permanently retrying. A reachable-but-incompatible Redis is actively dangerous here (same failure class documented in the sibling LexCore plan): briefly pointing `REDIS_URL` at the only other locally-running Redis (a native Windows 3.0.504 instance on port 6379) let Ondi's plain `ioredis` calls work, but crashed the whole process on the very next tick when BullMQ's own version check ran — confirmed via the crash log, then reverted. Tested the obvious hypothesis this raises for the Phase 2 vitest `describe()`/`config` crash — that a Redis-dependent module throwing during Vite's SSR transform was the cause — by rerunning `platform-parties.test.ts` with Redis now actually reachable: same crash, identical stack. Ruled out; the real cause is still unknown.

## Phase 4 — Tuma pilot (done, live-verified)

## Phase 5 — Production readiness (done, live-verified)

Scoped to the new surfaces this directive actually built (Phases 2-4) rather than re-auditing the whole pre-existing platform — that's where the real, untested risk is.

- **Tenant isolation / cross-tenant ID smuggling, proven at the database level, not just the app level**: confirmed `relrowsecurity` + `relforcerowsecurity` are both true for every tenant-scoped table this phase touches (`parties`, `party_external_refs`, `vehicle_vendors`, `api_keys`, `ondi_oauth_consents`). `oauth_resource_scopes` correctly has RLS *disabled* — it's a platform-level catalogue with no `tenant_id` column, same shape as `app_status`/`package_features`, not a gap. Then simulated the exact bug class CLAUDE.md calls out: a session scoped to tenant B querying tenant A's real party row (a) with an explicitly wrong `tenant_id` filter in the app code, and (b) with no `tenant_id` filter at all. Both returned nothing; an UPDATE attempt under the same conditions affected 0 rows and the row's data was unchanged afterward. RLS — not app-level diligence — is what actually stopped it in both cases.
- **Visibility boundary holds for the new no-human actor path**: `platform-parties.routes.ts`'s `actor.id = null` design (added while fixing the UUID-cast bug in Phase 3) means an API-key caller can only ever match `partyVisibleSql`'s `visibility = 'TENANT'` clause — every owner/share/team/department clause needs a real user id and null can never satisfy them. Verified directly: a real `PRIVATE`-visibility party owned by a real user was invisible to a `platform.parties`-scoped API key's search, even by exact name. A deliberate, correct consequence of treating "no human" as actually meaning no access to anything a human would have to specifically own or be shared, not as a bypass.
- **Access audit trail**: `index.ts`'s existing global `onResponse` hook logs every authenticated request (session or API key) to `api_usage_events`. Confirmed directly against the real `tuma-pilot` tenant's own usage rows from Phase 4's live traffic — every `POST /v1/platform/parties` call is there with the correct status code and timestamp. Nothing new needed; the existing mechanism already covers the new route for free.
- **Idempotency**: already proven live in Phases 3 and 4 — repeated `POST /v1/platform/parties` calls with the same `external_ref` return the same party id and never create a duplicate (confirmed both via direct repeated calls and via the Tuma pilot's consignee-edit re-link).
- **Record linking / duplicate review**: no new duplicate-creation path was introduced. The new Parties API's search is exact-ish (ILIKE, properly escaped) with no fuzzy auto-merge, consistent with `party.service.ts`'s own long-standing stance that merging two records is always a deliberate, reviewed step, never automatic — the new surface doesn't weaken that.
- **Role overlap**: by design, the new route checks the API key's `platform.parties` scope and its generic `read_only` flag, not `acting_role` — consistent with how every other API-key-gated route in this codebase works (scopes are the real ceiling; `acting_role` only matters for session-shaped checks like `requireRole()`, which API keys don't go through here intentionally). Not a new gap; matches the existing model.
- **API compatibility**: not applicable — `/v1/platform/parties` is a brand-new route with zero existing consumers to break.
