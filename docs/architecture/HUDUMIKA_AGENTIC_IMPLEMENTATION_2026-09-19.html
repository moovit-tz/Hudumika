ADR-001

One agent spine, not another chatbot

The current chat is useful but structurally narrow: it presents a conversation page over four read-only tools. Hudumika needs a governed execution surface that understands the user, tenant, application context, permissions, evidence and approval requirements.

Remove

/ai/chat page

Delete the sidebar entry and standalone page after the Agent workspace reaches parity.

Preserve

Memory and conversations

Migrate existing threads and explicit personal/workspace memory; do not erase user history.

Replace with

/agent

A task-oriented workspace for investigation, plans, approvals, evidence, runs and reusable agent skills.

Scope clarification: removing /ai/chat means removing the visible web route. The backend /v1/ai/chat cannot be deleted on day one because Calls and the Google Workspace sidebar currently consume it. It becomes a temporary compatibility adapter and is removed only after those callers migrate.

Target architecture

Governed execution path

1. RequestUser instruction, Studio trigger or domain event.
2. Agent runtimeIntent, context, plan, model selection and stop conditions.
3. Policy decisionAllow, deny or require human approval.
4. Typed toolValidated, tenant-scoped and idempotent service operation.
5. Evidence & auditResult, sources, actor, cost, changes and next action.

Agent is not the authority

The initiating user supplies intent. Ondi and policy determine authority. The tool performs the operation. The agent cannot expand its own permissions.

Model is not the database

Authoritative totals, statuses and calculations come from tools. The model explains results and proposes actions but does not invent operational state.

Controlled decommission

How /ai/chat is removed safely

Step 1

Freeze the legacy page

  • No new features in AIChat.tsx.
  • Add telemetry for page and API consumers.
  • Inventory deep links and saved bookmarks.
Exit: all callers and data dependencies documented.
Step 2

Launch /agent at feature parity

  • Threads, conversation history and explicit memory are available.
  • The four existing read tools work through the new registry.
  • Existing conversation IDs remain valid.
Exit: parity tests and tenant isolation checks pass.
Step 3

Remove the visible route

  • Delete Chat from AIShell navigation.
  • Redirect /ai/chat to /agent for one release.
  • Then remove AIChat.tsx and its route registration.
Exit: no internal links target the legacy page.
Step 4

Migrate embedded consumers

  • Calls uses an Agent session with meeting context.
  • Workspace sidebar uses the same Agent runtime with current-app context.
  • Both handle approvals and evidence consistently.
Exit: no frontend calls /v1/ai/chat.
Step 5

Retire the compatibility endpoint

  • Return deprecation headers before removal.
  • Move the handler to /v1/agent/runs.
  • Keep database history; remove only dead routing code.
Exit: production logs show zero legacy requests for 30 days.

Tenant isolation is mandatory: every table carries tenant_id, every query uses an explicit tenant predicate, and all database work runs inside withTenant(). A referenced entity ID must be verified as belonging to the same tenant before tool execution.
Interface contract

Agent API replacing chat

Method and routePurpose
POST /v1/agent/runsStart an agent run from a user goal, app context or domain event.
GET /v1/agent/runs/:idReturn current state, plan, evidence, steps, approvals and artifacts.
POST /v1/agent/runs/:id/messagesContinue or correct a run without creating a disconnected chat thread.
POST /v1/agent/runs/:id/cancelStop future steps; never pretend completed side effects were rolled back.
POST /v1/agent/approvals/:id/decisionApprove or reject using the authenticated human identity.
GET /v1/agent/toolsReturn tools visible to the current user and application context.
GET /v1/agent/threadsExpose migrated conversation history.
GET/POST/DELETE /v1/agent/memoryManage explicit personal or authorised workspace memory.

Transport: start with server-sent events for run progress and approval notifications. The work is server-to-client streaming; WebSockets are unnecessary until bidirectional real-time requirements actually exist.

Release gates

Definition of production-ready

Security and correctness

  • Cross-tenant access tests cover every tool.
  • Write tools are idempotent.
  • Agent cannot invoke undisclosed tools.
  • PII is redacted from provider logs and telemetry.
  • Approval cannot be replayed after expiry or execution.
  • Tool outputs—not model prose—drive authoritative state.

Product and operations

  • Every answer distinguishes recorded, derived, estimated and missing data.
  • Claims link to accessible evidence.
  • Users can cancel, correct and inspect runs.
  • Mobile approval and run views are usable.
  • Latency, tokens, cost and failures are observable.
  • Provider failure produces a recoverable run, not lost work.
First proof journey: ask which completed shipments are ready to invoice, receive a source-linked worklist, preview invoices, submit consequential actions for approval, execute each approved operation exactly once, and inspect the complete audit trail.
