2. Surfaces that are unaffected

A. Explicit shared-component overrides

These pages use the correct shared component but pass variant="…". That prop sets data-variant, whose component selector overrides the root data-tabs choice. This is deliberate behavior in the current API, but conflicts with the requested “one selection affects all tabs” policy.

Budgets.tsx · ComplyAgencies.tsx · ComplyLegal.tsx · FinancePayments.tsx · Recruitment.tsx · Overtime.tsx · Settings.tsx · TrackingDriverDetail.tsx · TrackingShipments.tsx · TrackingTrailers.tsx · TrackingVehicles.tsx

The Design System page also forces segmented for its composition example; that demo is not a production navigation surface. CommandCenter.tsx manually applies data-variant="segmented" to raw shared CSS classes and therefore also bypasses the selection.

B. Bespoke tab controls

These are buttons/divs with local state and page CSS. They never render ds-tabs-list/ds-tabs-trigger, so neither the global variant nor tab sizing tokens can reach them.

C. CSS that can partially mask the global appearance

Bliss.css styles active and hover states for bliss-inbox-tab-trigger on top of the shared component. Billing.css customizes active count badges. These do not fully disconnect the control, but can make a chosen variant look inconsistent. Inline styles on many shared TabsList/TabsTrigger instances similarly override layout, font size, background, width or spacing.

3. Why coverage is incomplete

  1. The component API permits policy bypass. variant? is public and has higher-priority selectors than the platform default.
  2. There is no enforced single tab primitive. Historic pages implemented tabs as ordinary buttons before the global component existed.
  3. “Tabs” and “filters” were treated as different visuals. Several status/category filters are functionally tabs but retain bespoke chip or card UI.
  4. No lint or CI rule protects coverage. New role="tablist", *-tabs classes, or local active-tab styles can be introduced without detection.
  5. No browser regression suite exists. Type checking cannot prove that all six variants remain usable on desktop, dark mode, and mobile.
  6. Persistence validation is permissive. The API accepts an arbitrary record rather than validating the tabs enum and numeric bounds. The typed admin UI is safe, but malformed external requests could save invalid values.
  7. Initial rendering uses local/default data before the GET resolves. A new browser can briefly render the default underline style before the stored global setting arrives.

4. What implementation requires

Phase 1
Policy
Decide whether any local variant is allowed. For the requested strict global behavior, remove production variant/data-variant overrides and reserve an override only for the design-system specimen via an explicitly named preview-only API.
Phase 2
Migration
Replace genuine bespoke tabs with Tabs, TabsList, TabsTrigger, and TabsContent. Preserve route/state behavior, counts and icons. Do not mechanically convert wizards, radio-card choices, view toggles, or navigation links unless their semantics are actually tabs.
Phase 3
CSS cleanup
Remove page-local active-track/fill/border rules. Keep only content-specific composition classes (badge sizing, icon visibility, container width) that do not redefine the selected variant.
Phase 4
Guardrails
Add a design-system check that rejects production variant=, raw data-variant, and new tab-role implementations outside components/ui/tabs.tsx and an allowlist. Add a typed Zod schema for tabs.variant, radius, height and size.
Phase 5
Verification
Build a route inventory and exercise every migrated surface across all six variants, light/dark themes, keyboard navigation, 320/768/desktop widths, overflow rows and disabled states. Because the repository has no automated UI test suite, browser checks are required before calling migration complete.

5. Recommended acceptance criteria

  • Changing the admin selection updates every mounted, genuine tab strip without reload.
  • After a reload and on another device, the saved selection is restored from the platform API.
  • No production page passes a visual tab variant override.
  • All genuine tabs use the shared primitive and support arrow-key navigation, focus indication, aria-selected, and linked panels.
  • All six variants remain legible in light/dark mode and scroll horizontally on narrow screens.
  • Non-tab controls (wizard steps, radio cards, list selectors, navigation links) are documented as exclusions and use their own correct design-system primitive.
Estimated scope: medium-to-large frontend migration. The infrastructure does not need redesign; most work is component replacement, semantic classification, removal of local CSS, and route-by-route visual verification. The highest-value first pass is removing the 11 production overrides and migrating the confirmed CRM/Ondi/Studio bespoke strips.

6. Audit limitations

The local browser integration exposed no available browser instance during this audit, so rendered pages and authenticated runtime behavior could not be visually inspected. Findings are based on exhaustive source searches and direct review of the provider, persistence route, shared component, global variant CSS, explicit overrides and representative bespoke implementations. A live visual pass remains mandatory before implementation sign-off.
