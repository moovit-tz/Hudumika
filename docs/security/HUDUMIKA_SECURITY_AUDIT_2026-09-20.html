Executive summary

The platform has a strong foundation but several unsafe exceptions

Hudumika has forced Postgres RLS across tenant tables, explicit withTenant() usage, httpOnly session cookies, CSRF verification, global rate limiting, role gates, entitlement gates, production-default secret guards, SSRF protection and substantial adversarial audit history. Those controls materially reduce risk. They do not cover the new Agent execution path, fail-open webhooks, dependency exposure, browser script injection or several still-unclassified data surfaces.

Confirmed and actionable

Priority findings

Critical

SEC-001 — Agent tools bypass application-specific authorization

The Agent endpoint excludes only CUSTOMER accounts. Every other role receives the complete tool catalog. For policy tools, MANAGER and higher execute immediately. The execution context carries only tenantId, not the initiating user, permissions, app entitlement or grant. Consequently a manager can use the Agent to record a FinOps expense, publish an HR announcement or reassign support work even when the corresponding application route would not grant that authority.

agent-runtime.service.ts:36–41, 89, 133, 158, 199 · agent-registry.ts:125 · agent.routes.ts:131–141 · agent_tool_grants is created in migration 488 but never queried
Required: deny all tools by default; enforce agent_tool_grants, app entitlement and the underlying domain permission using initiator identity on every execution. Management rank must not be a substitute for Finance, HR, SEAL or support permission.
Critical

SEC-002 — Approval race can execute an approved tool more than once

Approval decision insertion, quorum counting, approval-state transition and tool execution happen in separate transactions without a row lock or atomic claimed/executed state. Two eligible approvers can race; both may observe quorum, both mark the approval approved and both call the tool. This can duplicate expenses, tasks, announcements or regulated actions.

agent.routes.ts:296–388 — decision insert, count, status update and runAgentTool() are separate operations; no SELECT … FOR UPDATE, execution claim or idempotency key
Required: claim an approval atomically inside one transaction, add executing/executed state and a unique idempotency key, then make every write tool idempotent. Add concurrent-request tests.
High

SEC-003 — Agent allows self-approval and loses actor attribution

An initiator with an eligible role can approve their own request. The later tool execution uses the approver's tenant but not the initiator or approver identity, and several Studio actions write system/null actor attribution. The resulting audit trail cannot reliably answer who requested, authorised and performed the effect.

agent.routes.ts:58–62, 310, 320, 367 · no comparison with agent_runs.initiator_user_id before decision
Required: prohibit self-approval for high/critical effects, pass initiator/agent/approver identities into tools, and persist all three on the domain event and affected record.
High

SEC-004 — Ondi authentik webhook fails open with a published fallback secret

If AUTHENTIK_WEBHOOK_SECRET is absent, signature verification is deliberately skipped. An unauthenticated caller can forge authentication events, create regulatory audit entries and trigger trust-score recalculation. This is an integrity and compliance failure even though the route does not directly issue a session.

services/ondi-api/src/routes/authentik-webhooks.ts:20, 38–55
Required: refuse production startup without the secret, always require HMAC in deployed environments, compare signatures with timingSafeEqual, add timestamp/replay protection and stop logging computed signatures.
High

SEC-005 — Other inbound integrations still fail open when secrets are unset

Meta WhatsApp, GPSWOX and the shared SMS webhook guard accept unsigned or un-tokened callbacks when their environment secret is missing. Twilio has provider-signature validation when a tenant auth token exists, but the wider posture remains configuration-dependent. A deployment mistake turns public callbacks into forgery surfaces.

webhooks.routes.ts:25, 111–117 · sms.routes.ts:669–675 · existing HUD-0040/HUD-0125 audit notes
Required: production boot must fail when an enabled integration lacks its verification secret. Disable the individual route when not configured; never accept unsigned traffic as a fallback.
High

SEC-006 — 35 production dependency advisories remain unresolved

npm audit --omit=dev reports 3 critical, 13 high, 18 moderate and 1 low advisories. Runtime-relevant chains include fast-jwt/@fastify/jwt, Fastify routing/static/Swagger, fast-xml-parser, mailparser, nodemailer, sanitize-html, Kysely and legacy request through OpenTimestamps.

npm audit --omit=dev --json executed 20 September 2026: 35 total production advisories
Required: separate reachable production advisories from build-only/transitive ones, upgrade in controlled groups, and add a CI threshold that blocks new critical/high runtime vulnerabilities.
High

SEC-007 — Platform SEO feature is intentional stored script execution

A SUPER_ADMIN can store arbitrary head/body HTML that is fetched publicly and executed in every browser using createContextualFragment. This is intentionally equivalent to platform-wide JavaScript execution. A compromised SuperAdmin session or malicious tag can read rendered PII, make same-origin authenticated requests and affect every tenant.

platform.routes.ts:209–238 · useSeoAnalytics.ts:75–86, 140–141
Required: remove raw scripts or restrict to allowlisted provider IDs. If retained, require step-up authentication, dual approval, immutable audit, explicit warning, version rollback and a CSP compatible with nonce/hash-based trusted scripts.
Medium

SEC-008 — Content Security Policy is disabled platform-wide

Helmet supplies other headers, but CSP is disabled to avoid breaking Swagger UI. This leaves every app with a weaker last line of defence against any future rendering or dependency XSS. Disabling CSP for the entire API/platform because one documentation route needs inline assets is too broad.

apps/api/src/index.ts:279–283
Required: serve documentation separately or apply a docs-specific policy. Deploy report-only CSP first, inventory required origins, then enforce nonce/hash policies on the application.
Medium

SEC-009 — Generic application errors may be returned directly

Postgres driver errors and Zod errors are normalised, but every other exception is passed to reply.send(error). Depending on Fastify environment and error contents, provider messages, internal assumptions or operational details may reach clients.

apps/api/src/index.ts:357–386
Required: return a fixed 500 body with a correlation ID; log the complete server-side error. Maintain an explicit safe application-error type for intended 4xx messages.
Medium

SEC-010 — Project OS lacks intra-tenant portfolio confidentiality

Project OS blocks CUSTOMER accounts and has tenant RLS, but portfolios/programs are tenant-wide. A low-privilege staff member can see confidential portfolios such as acquisition or strategic programmes. Existing tests explicitly document this gap. The historical schema-drift issue also remains marked open, and the full suite did not complete during this review.

project-os.routes.ts:14–27 · project-os-isolation.test.ts:138–153 · AUDIT_REGISTER HUD-0032
Required: add portfolio/project membership and permission resolution to every list/detail/mutation path; complete migration/schema parity and make the smoke suite a deployment gate.

Platform controls

What is set correctly and what is still missing

Controls working well

  • Restricted application DB role plus forced RLS.
  • Explicit tenant predicates and withTenant().
  • HttpOnly secure-in-production access/refresh cookies.
  • Double-submit CSRF check for cookie-authenticated writes.
  • CORS origin allowlist with credentials.
  • Global and route-specific rate limiting.
  • Tenant suspension, maintenance and IP-allowlist enforcement.
  • Refresh/guest/setup tokens rejected from normal APIs.
  • Production refusal for published JWT, DB, Onsite and signing defaults.
  • SSRF guard on previously vulnerable configurable destinations.

Controls missing or incomplete

  • Enforced CSP.
  • Fail-closed integration-secret policy.
  • Agent tool grants and domain authorization.
  • Agent separation of duties and idempotent approvals.
  • Data classification/model routing for AI.
  • CI dependency-vulnerability threshold.
  • Complete frontend security tests—only one web test file exists.
  • Agent-specific adversarial/concurrency tests.
  • Completed classification of non-tenant/report tables.
  • Consistent safe 500 responses for non-database exceptions.

Remediation order

What to fix before production

P0

Stop Agent write release

Disable write-capable Agent tools or the entire Agent route until grants, domain permissions, self-approval prohibition, atomic approval claims and idempotency are implemented and tested.

P0

Make all production webhooks fail closed

Require authentik, SMS, Meta and GPSWOX verification configuration at startup or disable those receivers. Rotate any test/default secrets.

P1

Patch reachable critical/high dependencies

Start with JWT/Fastify, static/Swagger, XML/mail ingestion and OpenTimestamps. Add audit enforcement in CI.

P1

Constrain platform-wide scripts

Remove arbitrary custom scripts or put them behind step-up authentication and dual control; deploy CSP in report-only mode and then enforce it.

P2

Close authorization and assurance gaps

Add Project OS ACLs, classify remaining global/report tables, normalise safe errors, add Agent concurrency tests and make the full API/web security suite deterministic in CI.

Method and evidence

How this review was performed

  • Read repository security directives and architecture conventions.
  • Enumerated 208 API route modules and all frontend application shells.
  • Reviewed shared Helmet, CORS, JWT, cookie, CSRF, rate-limit, entitlement, suspension and RLS controls.
  • Searched for unauthenticated routes, direct DB access, BYPASSRLS usage, public endpoints, raw HTML, child processes, filesystem access, outbound fetches, webhook verification and hardcoded/default secrets.
  • Reviewed the existing production-readiness audit register and current code rather than assuming previously fixed findings remain open.
  • Ran npm audit --omit=dev --json.
  • Counted 23 API/service test files, one web test file and zero Agent-specific test files.
  • Started the API suite; it timed out after approximately three minutes without a final result. The standalone Ondi service is not an npm root workspace, so its suite requires its own package-manager/environment invocation and was not reported as passing.
No destructive testing was performed. No tenant records, credentials, configuration or external systems were modified. Findings are based on code and local dependency metadata.
