01 · Product Overview
ClearOS — Customs Clearance & Freight Operations OS
ClearOS is a multi-tenant case management system for customs clearing and freight forwarding companies. The primary unit of work is the Shipment Case — a living object that owns documents, people, approvals, payments, communications, and time. Everything else orbits the case.
B2B SaaS Multi-tenant Mobile-first 1000+ customers/tenant 1M+ shipments/month 4,200+ locations
ℹ
Core design principle: The system never shows everything. It surfaces what needs action. Every screen answers one question: "What do I do next?" A field officer at Namanga border post sees 8 cases; a Dar HQ manager sees 4,287 — same codebase, different filters.
The 5 Core Views
1
Command Center (Ops Board)
KPI bar + shipments grouped by customer with collapsible rows. The primary operator view. Sorting by urgency — demurrage risk always floats to top. Role-filtered by location and assignment.
2
Shipment Detail Panel
Timeline (18 stages) + Communications log + Documents vault + Cost ledger. The single source of truth for one shipment. Slide-in panel on desktop, sheet on mobile.
3
Customer Portal
Separate app. Zero jargon. 5-step journey view, action needed tab, updates feed, document downloads, invoice. Auth via WhatsApp OTP or magic link email.
4
Analytics Dashboard
Bottleneck analysis by stage, officer performance, customer profitability, penalty patterns, SLA trends. Available V1. ML predictions added post 50k shipments of history.
5
Field Officer Mobile
Stripped-down single-case focus. Designed for border post: large touch targets, photo doc upload, offline-capable case view, WhatsApp-linked comms.

02 · Architecture
System Architecture Overview
Multi-tenant SaaS. Each clearing company is a tenant isolated at the database layer via Row Level Security. The system is horizontally scalable — each service can be scaled independently as load grows.
⚠
Scale constraint day 1: At 1M+ shipments/month, the shipments table exceeds 10M rows within year one. Partition by (tenant_id, created_at) from the first migration. Never retrofit partitioning onto a live 10M-row table.

Multi-Tenancy Strategy
Single database, tenant isolation via Row Level Security. Every table has a tenant_id UUID NOT NULL column. A PostgreSQL session variable app.tenant_id is set at connection time and enforced by RLS policies automatically.

-- Core tenants table CREATE TABLE tenants ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), slug VARCHAR(50) UNIQUE NOT NULL, -- 'msomi-freight' name TEXT NOT NULL, plan TEXT DEFAULT 'enterprise', created_at TIMESTAMPTZ DEFAULT NOW() ); -- Enable RLS on every tenant-scoped table ALTER TABLE shipments ENABLE ROW LEVEL SECURITY; ALTER TABLE customers ENABLE ROW LEVEL SECURITY; ALTER TABLE documents ENABLE ROW LEVEL SECURITY; ALTER TABLE expenses ENABLE ROW LEVEL SECURITY; ALTER TABLE messages ENABLE ROW LEVEL SECURITY; -- Single policy pattern applied to all CREATE POLICY tenant_isolation ON shipments USING (tenant_id = current_setting('app.tenant_id')::UUID); -- Set in middleware before every query: -- SET LOCAL app.tenant_id = '<uuid>'

04 · Shipment Case Module
Creating & Managing Shipment Cases
A case is created the moment documents arrive — email attachment, WhatsApp forward, manual entry, or API. The case ID is the reference used in all communications, notifications, and documents for its entire lifetime.
TypeScriptsrc/services/shipment.service.tscopy
class ShipmentService { async createCase(input: CreateShipmentInput): Promise<ShipmentCase> { const ref = await this.generateRef(input.tenant_id); // CLR-2025-XXXX const sla = computeSLA(input.type, input.eta); const shipment = await this.db.insert('shipments', { ...input, ref_number: ref, sla_deadline: sla, stage: 'DOCS_RECEIVED' }); // Open first stage in history await this.db.insert('stage_history', { shipment_id: shipment.id, stage: 'DOCS_RECEIVED', entered_at: new Date(), actor_id: input.created_by }); // Notify assigned officer + customer await this.notify.caseOpened(shipment); return shipment; } // Grouped list — primary command center query async listGroupedByCustomer( tenantId: string, filters: ShipmentFilters ): Promise<CustomerShipmentGroup[]> { const shipments = await this.db.query(` SELECT s.*, c.name as customer_name, c.id as customer_id, ARRAY_AGG(rf.type) FILTER (WHERE rf.resolved = false) as active_risk_flags FROM shipments s JOIN customers c ON s.customer_id = c.id LEFT JOIN risk_flags rf ON rf.shipment_id = s.id WHERE s.tenant_id = $1 AND ($2::text IS NULL OR s.stage = $2) AND ($3::uuid IS NULL OR s.customer_id = $3) GROUP BY s.id, c.id ORDER BY MAX(CASE WHEN rf.type = 'DEMURRAGE' THEN 1 ELSE 0 END) DESC, MAX(CASE WHEN rf.type = 'SLA_BREACH' THEN 2 ELSE 0 END) DESC, s.updated_at DESC `, [tenantId, filters.stage, filters.customer_id]); return groupByCustomer(shipments); // group in memory } }
Auto-Generated Case Reference
Case references follow the format CLR-YYYY-NNNN where NNNN is a sequential tenant-scoped counter. They must be collision-resistant across concurrent inserts and human-readable enough to use in WhatsApp and email.
SQLmigrations/004_ref_sequence.sqlcopy
-- Per-tenant per-year sequence using advisory locks CREATE TABLE ref_counters ( tenant_id UUID NOT NULL, year INT NOT NULL, counter INT NOT NULL DEFAULT 0, PRIMARY KEY (tenant_id, year) ); -- Atomic increment function CREATE OR REPLACE FUNCTION next_case_ref(p_tenant UUID) RETURNS TEXT AS $$ DECLARE yr INT := EXTRACT(YEAR FROM NOW()); seq INT; BEGIN INSERT INTO ref_counters(tenant_id, year, counter) VALUES(p_tenant, yr, 1) ON CONFLICT(tenant_id, year) DO UPDATE SET counter = ref_counters.counter + 1 RETURNING counter INTO seq; RETURN 'CLR-' || yr || '-' || LPAD(seq::TEXT, 4, '0'); END; $$ LANGUAGE plpgsql;
05 · Workflow Engine
Stage Transitions & SLA Management
The workflow engine owns all stage transitions. It validates prerequisites before allowing advancement, records every transition as an immutable event, starts SLA timers, and triggers notifications. A stage transition is an event, not a state update.
💡
Key insight: Store every stage transition in stage_history with duration. This is what powers analytics, SLA tracking, penalty detection, and the "which stage is our biggest bottleneck?" question. You cannot retrofit this if you skip it in V1.
TypeScriptsrc/services/workflow.service.tscopy
class WorkflowService { async advanceStage( shipmentId: string, actorId: string, note?: string ): Promise<ShipmentCase> { const s = await this.db.getShipment(shipmentId); const next = STAGE_SEQUENCE[s.stage]; if (!next) throw new Error('Already at final stage'); // Check all prerequisites are met const prereqs = STAGE_PREREQUISITES[next]; const unmet = prereqs.filter(p => !this.checkPrereq(s, p)); if (unmet.length) throw new StageBlockedError(unmet); await this.db.transaction(async (trx) => { // Close current stage with duration await trx.update('stage_history', { exited_at: new Date(), duration_h: hoursSince(s.stage_started_at) }, { shipment_id: shipmentId, stage: s.stage }); // Open new stage await trx.insert('stage_history', { shipment_id: shipmentId, stage: next, entered_at: new Date(), actor_id: actorId, note }); // Update shipment current stage await trx.update('shipments', { stage: next }, { id: shipmentId }); }); const sla = SLA_BY_STAGE[next]; await this.slaQueue.schedule(shipmentId, next, sla); await this.notify.stageAdvanced(s, next); return this.db.getShipment(shipmentId); } // Called every 15 min by cron async runRiskScan(): Promise<void> { const active = await this.db.query(` SELECT * FROM shipments WHERE stage NOT IN ('CLOSED','INVOICING') AND (free_time_end < NOW() + INTERVAL '48 hours' OR sla_deadline < NOW()) `); for (const s of active) { const flags = computeRiskFlags(s); await this.db.upsertRiskFlags(s.id, flags); if (flags.some(f => f.severity === 'HIGH')) await this.notify.riskDetected(s, flags); } } }

06 · Communications Hub
Unified Messaging — WhatsApp, Email, Internal
All communications are stored as messages attached to the shipment case. Channel (WhatsApp, Email, WeChat, in-app) is a message attribute, not a separate system. A manager can open any case and see the complete conversation history regardless of which channel was used.
ℹ
Channel strategy: Tanzania operators and customers → WhatsApp (default). Enterprise / European partners → Email. Internal team → in-app + WhatsApp. Never force a channel. Read the customer's preferred_channel field and use it.

07 · Finance Engine
Cost Ledger & Margin per Shipment
Every shipment has a running P&L. Revenue (clearance fee, transport, agency) and expenses (duties, port, inspection, haulage) are recorded as immutable ledger entries. The system computes estimated gross margin in real-time. Most clearing agents today do not know their actual profit per job — this module changes that.
⚠
Important distinction: Government duties and taxes are pass-through items — collected from the customer and paid to TRA. They are not your revenue or expense. Flag them as is_passthrough = true and display them separately in the P&L to avoid inflating or deflating your actual margin.
TypeScriptsrc/services/finance.service.tscopy
interface ShipmentPnL { revenue: number; // clearance + transport + agency fees expenses: number; // inspection + haulage + labour passthrough: number; // duties + port charges (not yours) gross_margin: number; // revenue - expenses margin_pct: number; // gross_margin / revenue accruing: number; // storage/demurrage accumulating now status: 'OPEN' | 'INVOICED' | 'PAID'; } class FinanceService { async computePnL(shipmentId: string): Promise<ShipmentPnL> { const expenses = await this.db.getExpenses(shipmentId); const rev = expenses .filter(e => e.is_revenue) .reduce((s, e) => s + e.amount_tzs, 0); const exp = expenses .filter(e => !e.is_revenue && !e.is_passthrough) .reduce((s, e) => s + e.amount_tzs, 0); const pass = expenses .filter(e => e.is_passthrough) .reduce((s, e) => s + e.amount_tzs, 0); return { revenue: rev, expenses: exp, passthrough: pass, gross_margin: rev - exp, margin_pct: rev > 0 ? (rev - exp) / rev * 100 : 0, accruing: await this.computeAccruingCharges(shipmentId), status: await this.getInvoiceStatus(shipmentId) }; } async generateInvoice(shipmentId: string): Promise<Invoice> { const pnl = await this.computePnL(shipmentId); const inv = await this.db.createInvoice({ shipmentId, ...pnl }); await this.notify.invoiceGenerated(inv); return inv; } }

09 · Analytics Module
Operational Intelligence — Bottlenecks, Performance, Risk
Analytics are derived entirely from stage_history. This is why recording every stage transition with duration is non-negotiable from day one. Every useful management question can be answered by aggregating that single table.
💡
The most valuable query in the system: Average hours spent per stage, by shipment type, over the last 90 days. This tells you instantly where your operation is losing time. Run it monthly and share with customers.
SQLqueries/bottleneck_analysis.sqlcopy
-- Average hours per stage (last 90 days) SELECT stage, ROUND(AVG(duration_h), 1) AS avg_hours, ROUND(PERCENTILE_CONT(0.9) WITHIN GROUP (ORDER BY duration_h), 1) AS p90_hours, COUNT(*) AS case_count, SUM(CASE WHEN duration_h > sla_limit THEN 1 ELSE 0 END) AS sla_breaches FROM stage_history sh JOIN shipments s ON s.id = sh.shipment_id WHERE sh.tenant_id = :tenant_id AND sh.entered_at > NOW() - INTERVAL '90 days' AND sh.duration_h IS NOT NULL GROUP BY stage ORDER BY avg_hours DESC; -- Officer performance: cases closed, avg days, penalties caused SELECT u.name, COUNT(DISTINCT s.id) AS cases_closed, ROUND(AVG( EXTRACT(EPOCH FROM s.updated_at - s.created_at) / 86400 ), 1) AS avg_days, COUNT(rf.id) AS penalties_caused FROM shipments s JOIN users u ON s.assigned_to = u.id LEFT JOIN risk_flags rf ON rf.shipment_id = s.id AND rf.type = 'PENALTY' WHERE s.tenant_id = :tenant_id AND s.stage = 'CLOSED' AND s.updated_at > NOW() - INTERVAL '30 days' GROUP BY u.id, u.name ORDER BY cases_closed DESC;

13 · V1 Scope
What To Build First — Strict Boundaries
V1 must be adoptable in under 1 hour by a clearing agent currently using Excel + WhatsApp. If learning ClearOS takes longer than reopening Excel, it will not be adopted. The goal is to replace chaos — not to build a perfect system.
🚫
Hard exclusions from V1: ML predictions, trade finance, WeChat integration, deposit refund automation, full accounting integration, mobile offline mode, TANCIS/CargoWise API integration, customer sentiment scoring, multi-currency. Add these only when customers pull for them.
1
Shipment Case — Create & Track
Create case with customer, goods, BL, type. Advance through 18 stages. Record blocker at each stage. Store full stage history. Full stage history replaces Excel alone.
2
Document Vault
Upload docs, mark required/optional per stage. Block advancement if required doc is missing. Download all docs as ZIP. Every document stored in MinIO with the case as parent.
3
Command Center — Grouped by Customer
Shipments grouped by customer, collapsible rows, sorted by urgency. KPI bar. Column headers: ID, type, goods, stage, status, officer, days. Role-filtered views. Detail slide-in panel.
4
WhatsApp Auto-Notifications
Daily 08:00 EAT status update. Trigger on stage advance. Missing doc reminder (24h, max 3 sends). Demurrage alert when free time <48h. This is the feature that replaces the agent's morning copy-paste routine.
5
Cost Ledger per Case
Record revenue and expenses per case. Show estimated margin. No accounting integration needed in V1 — just the numbers attached to the case.
6
Risk Flags — Demurrage & SLA
Cron every 15min. Flag free time <48h. Flag stages exceeding SLA. Surface on command center KPI bar and case urgency indicator. Alert manager via in-app and WhatsApp.
7
Customer Portal (Read-Only V1)
Customer sees their shipments in plain language. 5-step journey. Updates feed. Document download. Auth: WhatsApp OTP or magic link. No upload, no payment, no chat in V1.
