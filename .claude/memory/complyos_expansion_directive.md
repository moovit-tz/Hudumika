On 2026-07-19, after I finished the first ComplyOS full-stack build-out (see the approved plan that was at `C:\Users\Viden\.claude\plans\tidy-hatching-book.md` — packages A-D: real Agencies/Calendar/BRELA-import/notification fixes, AI obligation scan, document OCR auto-fill, Legal Firm Marketplace v1, agency-adapter workflow wiring), the user sent a large follow-on directive while going to sleep, explicitly saying "always proceed" — i.e. keep executing without stopping to ask, across as much of this as possible, and recall it fully afterward since they wouldn't be available to repeat it.

**Why:** the user wants ComplyOS to go from "functionally real but visually/architecturally rough" to production-grade: on-brand, backed by real linked data (not just tenant-scoped in isolation), fully CRUD-capable, responsive, using the platform's established form patterns, cross-linked to other Hudumika apps, and ultimately a convincing sales instrument to close new subscribers.

**The directive, verbatim intent, broken into parts:**

1. **Design system compliance** — app buttons and colors in ComplyOS must be picked from the platform design system, not hardcoded hex. Confirmed token set in `apps/web/src/index.css`: `--teal`/`--teal-l`/`--teal-m` (brand primary — not a generic hue), `--gold`/`--gold-l`, `--red`/`--red-l`, `--green`/`--green-l`, `--blue`/`--blue-l`, `--purple`/`--purple-l`. Reusable classes already exist: `.badge-teal/gold/red/green/blue/purple/grey`, `.sp-*` status pills, `.ct-*`, `.urg-*`. ComplyOS's current agency-class colors (gov/tax/social/reg/fin) and calendar severity colors (green/blue/amber/red) and legal-firm brand colors are still hand-rolled hex in `ComplyOS.css` / `ComplyLegal.tsx` and need remapping onto these tokens/classes.

2. **Real CRM-linked data, full CRUD, no mockups** — ComplyOS's tables (`comply_certificates`, `comply_applications`, `comply_obligations`, `comply_legal_engagements`, etc., all in `apps/api/src/db/migrations/031_complyos_core.sql` + `095_comply_profiles_obligation_rules.sql` + `096_comply_legal_marketplace.sql`) are currently only `tenant_id`-scoped — **zero link to the real `customers` table** (`apps/api/src/db/migrations/002_core_tables.sql`, tenant-scoped CRM clients, real working CRUD at `apps/api/src/routes/customers.routes.ts`). User wants ComplyOS entities linked to real CRM clients (the PRD's "multi-entity" concept — a tenant manages compliance for its own subsidiaries/clients, modeled as CRM customer records), sample permits/obligations/workflow data seeded as real DB rows (not frontend-hardcoded), and every entity editable/deletable through the UI, not just creatable.

3. **Full responsiveness** — apply the platform's established pattern: `useIsMobile()` hook (`apps/web/src/hooks/useIsMobile.ts`, breakpoint from `--mobile-breakpoint` CSS var, SuperAdmin-configurable) + inline grid-collapse (`gridTemplateColumns: isMobile ? '1fr' : 'repeat(n,1fr)'`). Best reference implementation in the codebase: `apps/web/src/pages/Leads.tsx` (master/detail collapse, profile grid collapse, form grid collapse all in one file). No table→card component exists platform-wide — tables just get `overflow-x: auto` on mobile, that's the convention, not a rewrite to cards.

4. **Cross-app API interlinking** — PRD calls for ComplyOS↔TrustID and Bliss↔ComplyOS hooks. **Confirmed via investigation: TrustID does not exist anywhere in this codebase** — not in `AppId`, no routes, no tables, nothing. It is PRD-only fiction; `oneid`/Ondi is a *different* thing (SSO/identity admin, not a trust-score service). Building a real TrustID integration means inventing an entire new app from scratch — flagged as out of realistic scope for "just wire it up," should not be faked. **Bliss is real** (`support_tickets` table, `apps/api/src/routes/*.ts` support routes, `BlissShell.tsx`). No generic event-bus/webhook-dispatch mechanism exists anywhere in the platform — the only precedent for cross-app triggering is a bespoke direct-service-call-within-one-request (see the WhatsApp-webhook-auto-creates-support-ticket path in `webhooks.routes.ts`). Any Bliss→ComplyOS hook should follow that same ad hoc convention, not invent a new abstraction.

5. **Multi-step forms instead of popups** — the modals I built in the first pass (`ComplyOnboardingModal.tsx`, the `AddReminderModal` in `ComplyCalendar.tsx`, the `EngageModal` in `ComplyLegal.tsx`, the "New Application" modal in `ComplyApplications.tsx`) are single-screen popup forms and should become proper multi-step wizards (step indicator, next/back), per the user's explicit preference stated here — this is a **standing UI preference for ComplyOS's forms going forward**, not a one-time fix.

6. **Sales/marketing wizard page** — build a new, separate deliverable: a persuasive, interactive multi-step "what ComplyOS can do" sales page, modeled visually/functionally on legal.io and Smokeball's marketing sites (user gave both as explicit references), written in the voice of an experienced salesperson, intended to convert prospects into subscribers. This is a marketing artifact, not a gated in-app feature — ends in a subscribe/contact CTA.
